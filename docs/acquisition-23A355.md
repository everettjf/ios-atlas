## Interpretation and limits

A dyld image's install name is a logical path; its executable may be inside the cache without a separate regular file at that path. The [Foundation example](../research/23A355/Foundation.md) shows this directly. This dataset covers all 127 IPSW archive members, mounted contents of all five disk images, the iOS and DriverKit cache families, and both kernelcache variants. Other firmware payloads have hashes and BuildManifest roles but have not been decompiled. Runtime-generated data remains outside this official-distribution catalog.

All 621 launchd plists in the scanned FileSystem image parsed successfully. Their executable declarations resolve directly to a path in the three installed-system image catalogs for 604 plists; nine more map through the explicit AppOS/SystemOS cryptex prefixes; seven have no matching path in those scans; one jetsam configuration has no executable declaration. “Unresolved” is a bounded catalog result, not proof that an executable never exists on a running device. Five labels occur in two variant plists, so service records are keyed by plist path rather than label. See the [SpringBoard chain](../research/23A355/SpringBoard.md) for a worked example.

The 613 resolved launchd plist records point to 600 distinct executable files. All 600 parse as Mach-O executables: 599 arm64e and one arm64. Their load commands declare 14,843 direct dylib imports, of which 14,777 have an exact install-name match in the indexed iOS cache, four match separate regular files in the three scanned installed-system images, and 62 match neither indexed source. Of those 62, 61 are weak loads; the one required load is `FusionPluginKit` from `fusiond`. These are **direct static declarations only**: no transitive dependency closure, `@rpath` expansion, load-time condition, or runtime loading is claimed. An unmatched name is not evidence that a running device cannot resolve it.

Every image in the intact iOS arm64e cache parsed as a Mach-O with the UUID listed in the cache inventory (4,169 dylibs and one dynamic linker image). Their load commands declare **90,837 direct dylib loads**: 64,687 ordinary, 25,772 weak, 171 upward, and 207 re-export. An exact install-name match exists for 90,806 loads within this cache family. The other 31 loads use 20 distinct names, and all 31 are weak. The website shows both outgoing declarations and reverse direct importers; it does not imply that these loads resolved or that any process executed a library. The collector stores a resumable checkpoint outside Git and verifies each image UUID against the original cache inventory. A second run from the complete checkpoint produced byte-identical output.

The Dependency reach view performs breadth-first search over only the 90,806 exact in-cache install-name matches. It records one shortest declaration chain per reachable image, guards against cycles, and offers separate paths excluding or including `LC_LOAD_WEAK_DYLIB`. For Foundation, those modes reach 123 and 1,353 other images respectively; for SpringBoard.framework, 1,518 and 1,680. These counts are properties of this static cache graph. They do not model dyld conditions, `@rpath` expansion, dynamic loading, process-specific environment, or actual execution. The standalone graph logic is checked for cycles, weak edges, unmatched targets, and shortest-path reconstruction before deployment.

The separate DriverKit cache also has a [named function-symbol catalog](../research/23A355/DriverKit-Function-Surface.md): **65,668** unique `__text` symbol records across all 51 images, with each address checked against its image section and each image UUID checked against the cache inventory. All three cache files were re-extracted from the official IPSW and matched the recorded SHA-256 values. Class dumps for all 51 images yielded no ObjC class or method declarations. These symbol names are not a complete function inventory.

The separate DriverKit cache contains 51 arm64e dylibs with **209 direct loads**: 175 ordinary, two weak, 19 upward, and 13 re-export. Every load has an exact install-name match within that DriverKit cache family. The site keeps this graph separate from the iOS graph, preserving their different cache UUIDs and platforms.

The iOS cache Objective-C optimization table contains **216,890 class entries** associated with **3,443 in-cache images**. Its command output gives each class name, metadata address, and image basename. All 168,100 entries with unique image basenames resolve directly to an install name. For the 48,790 entries with a basename shared by multiple images, the collector inspects the candidates' non-linkedit Mach-O segment ranges, verifies their UUIDs, and selects the one containing the class address. All 48,790 resolved uniquely in this build. These are class metadata entries, not live object instances or methods executed at runtime. Duplicate class names remain separate records. The DriverKit cache is outside this Objective-C class index.

The per-image method catalogs now cover **all 4,170 iOS cache images** with **3,065,801 Objective-C method entries**, **217,455 rendered classes**, and **10,623 categories**. Each recorded IMP falls within its defining image's `__TEXT` segment. The first 69 catalogs record an extracted analysis derivative hash; 4,101 newer catalogs come directly from the intact cache after all 80 family members were checked by SHA-256 against the official firmware catalog. Of the 4,170 images, 1,014 have zero method entries, including 406 for which `ipsw class-dump` emitted an empty file. Sixteen images absent from the ObjC optimization class table nonetheless contain 119 entries in their class dumps. Ten method selectors are unavailable and remain null. The public image explorer shows a short source-derived overview for each library and loads a compressed method bucket on selection. This is a horizontal static metadata inventory, not an implementation or runtime behavior description. See the [coverage note](../research/23A355/Method-Catalog-Coverage.md), [research TODO](research-todo.md), and the [Foundation](../research/23A355/Foundation-Method-Surface.md) and [SpringBoard](../research/23A355/SpringBoard-Method-Surface.md) examples.

The [framework introduction pass](../research/23A355/Framework-Introduction-Coverage.md) links 213 of 227 exact top-level iOS framework images to matching Apple Developer framework pages. One separate DriverKit image has a sourced introduction. Each catalog entry records the retrieved document SHA-256 and date. The short framework descriptions concern documented API families; they do not validate behavior or public availability of every symbol in this exact cache image.

The [standalone Swift pass](../research/23A355/Standalone-Swift-Dump-Coverage.md) inspected all 3,363 physical Mach-O files with exact file hashes and UUIDs. The tool reported no Swift information for 2,068 files. Its text contains 282,145 declaration lines and 294,746 member or protocol-requirement lines in the remaining files; 133 outputs were partially parsed because of malformed lines, which remain explicit in the site and catalog. These rows do not establish in-file type ownership or a complete method surface.

The same cache's Objective-C protocol optimization table contains **67,351 entries**. For 49,497 entries, the reported image basename matches exactly one cache image. The remaining 17,854 entries use 206 basenames shared by multiple images; the catalog retains those candidates without assigning a definition site. Some protocol table addresses point into shared metadata outside the named image, so address containment is not used to resolve this table. Repeated names and addresses remain separate table entries. The protocol index does not assert runtime conformance or use.

The intact iOS cache's Swift type-conformance output contains **590,036 records** across **1,553 cached images**. The segment collector verified the UUID and enumerated Mach-O segments for all 4,170 images, including one zero-size segment for which `ipsw` omits size keys. The conformance collector checks every type, protocol, and conformance descriptor address against exactly one non-`__LINKEDIT` segment of an image with the reported basename. This resolves the 53,365 conformance descriptors bearing a basename shared by multiple cache images, without relying on basename alone. The output contains raw symbols for 276,402 types, 557,648 protocols, and 271,691 conformance descriptors; remaining names are unavailable in this source. The 591 `next is duplicate` markers are retained as source markers, not collapsed into a unique-conformance count. All records remain separate, including repeated names and addresses. The public index and 64 compressed buckets carry exact source identity and per-bucket SHA-256; the site loads only the bucket needed for the selected image. These static records do not prove any process loaded a type or used a conformance at runtime.

A trusted device with matching product and build was observed over read-only root SSH through USB. Its RootHide view uses `/rootfs` for the base system while `/` is a jailbreak-specific namespace. The main live cache is under `/private/preboot/Cryptexes/OS/System/Library/Caches/com.apple.dyld/`. All **80** files in that live arm64e cache family matched the corresponding extracted IPSW files by SHA-256; there were no extra or missing files in that family. The live `/rootfs` volume walk counted 430,745 paths including its root, but that namespace is not directly comparable to the three IPSW image catalogs. The separate DriverKit cache also matched the device for all three files by SHA-256; it is outside the 80-file iOS cache count. This live observation is not a clean pre-jailbreak snapshot; IPSW-versus-device differences alone cannot establish jailbreak causation. No private device identifiers are published.

The [filtered device catalog](../catalog/ios/23A355/device-rootfs.json.gz) contains **430,719** paths and types from `/rootfs/Applications`, `/rootfs/Library`, `/rootfs/System`, `/rootfs/bin`, `/rootfs/sbin`, `/rootfs/usr`, and `/rootfs/private/etc`. It excludes `/private/var`, preboot, `dev`, all other roots, and the jailbreak namespace. Every published device path and type was checked against the official IPSW catalogs and matched a record there; the site build refuses to publish any unmatched device entry. This is a path/type check, not a content hash check. The device catalog is a live, filtered observation and does not represent every file on the phone.

The [stock versus device note](../research/23A355/Stock-Device-Boundary.md) derives a tighter same-path comparison. Within those seven roots, the three official images have 434,852 unique path/type pairs; 430,719 appear in the filtered device index and 4,133 do not at the same path. All 430,719 device pairs occur in FileSystem. The 4,133 unmatched stock pairs come from the separate SystemOS (2,904) and AppOS (1,229) images. They may appear under different live cryptex paths, and this result cannot establish jailbreak causation or whole-device absence.

The collector is `tools/collect_device.py`. It requires an existing trusted SSH key and pinned known-hosts file; it never stores those paths or device identifiers in the output. For a USB tunnel to port 22326, invoke it with `--port 22326 --identity <KEY> --known-hosts <KNOWN_HOSTS> --product iPhone12,1 --build 23A355 --output .local/device-rootfs.json.gz`, review the local result, then copy it into `catalog/ios/23A355/` only after the official-path validation succeeds.
