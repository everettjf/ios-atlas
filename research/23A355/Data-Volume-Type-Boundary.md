# What did the partial data-volume type passes observe?

Target: the connected iPhone 11 (`iPhone12,1`) on iOS 26.0.1 (`23A355`). A read-only follow-up on 2026-11-06 UTC scanned the Data and Mobile data mount views separately. Their private snapshot manifest has SHA-256 `7a5e8ed0996521bd534af8561e5ed36fa98e6b2ec73be34529096e076e76a5d1`. These are **partial** views: `find` encountered the same 16 and 57 protected directories as the earlier snapshot, with no overlap between the two error sets. All 73 errors were `Operation not permitted`. A separate read-only `stat` attempt also returned `Operation not permitted` for every one of those directory paths. The underlying protection mechanism and descendant counts are unknown. No protected directory was bypassed.

A later bounded root-SSH probe checked **all 73** of those exact paths without listing their contents. Every parent directory's metadata was readable (70 parents had mode `755`, two `777`, one `700`), while `stat` on every target and `find -maxdepth 0` on every target failed. A further read-only `stat` sample of ten target directories as the `mobile` account also failed for all ten. The result rules out a missing or unreadable parent as a general explanation; it does not identify the mechanism enforcing the denial. The aggregate probe is kept privately at `.local/live-device-data-followup-20261106/protected-access-probe.json`. iCTRL's port 8200 was not listening at that observation time, and `notifyutil` was absent from the device shell, so those passes could not check lock state. The owner subsequently confirmed that the phone **was already unlocked**; a fresh root-SSH sample still returned `Operation not permitted` for ten protected targets. The earlier lock-state explanation is no longer a useful working assumption.

The root shell reported UID 0, `platform-application = true`, and `com.apple.private.security.no-sandbox = true`. It could `stat` `/rootfs` and `/rootfs/private/var`, but could not `stat` the ten protected targets. [Apple's Data Vault documentation](https://developer.apple.com/documentation/system/fileflags/datavault) describes entitlement-gated filesystem access, and [Apple Platform Security](https://support.apple.com/en-is/guide/security/sec93292bfa6/web) says this protection is enforced independently of the app sandbox. These sources make Data Vault **a candidate explanation**, not an identified cause for these paths. An [Apple DTS explanation](https://developer.apple.com/forums/thread/114452) also cautions that the `UF_DATAVAULT` file flag is not a universal detector.

A temporary, signed, read-only `getattrlist`/`getattrlistbulk` probe was calibrated before interpreting flags. The SSH shell could see an ordinary `/rootfs/private/var` control path, but the probe returned `ENOENT` for that same path and all 73 protected targets; it therefore had a different effective path view and **cannot establish whether any target has `UF_DATAVAULT`**. Adding platform and no-sandbox entitlement keys to the temporary probe did not change that result. The aggregate and invalid-for-flag-inference calibration are kept privately at `.local/live-device-data-followup-20261106/protected-flags-probe.json`. The temporary executable and directory were removed after each run. No protected directory was bypassed; its descendants remain unknown.

- **Data:** The later snapshot and type pass had exactly the same 23,490 unique reachable regular-file paths. Of these, 303 descriptions contained a Mach-O signature: 179 executables, 112 dylibs, 7 bundles, and 5 dSYM companion files. All candidates are within private app-bundle storage; no path or binary is public.
- **Mobile data:** The snapshot and type pass each saw 29,500 unique paths, but 34 paths appeared and 34 disappeared between passes. Three descriptions contained a Mach-O signature: 2 executables and 1 dylib in private mobile app or media storage. The changing path set prevents a stable exhaustive candidate count for this view.

The `file-5.43` passes returned nonzero solely because `find` could not traverse the same protected directories recorded by their snapshots. Their stderr bytes matched the corresponding snapshot stderr files exactly; none of the emitted file descriptions reported a read error. The private NUL-delimited type outputs have SHA-256 `c69c3b41abe03f2078467795cc625725ce84030ad8893ce15333d7968c2e9edb` (Data) and `990a9222727d8483fe8288ca11c2afab610c109f6fa2247e8feaf2d0f6278472` (Mobile data). Raw paths, filenames, and contents remain under ignored `.local`.

These are **type candidates**, not byte-verified Mach-O catalog entries. The 5 dSYM companion files are counted as Mach-O signatures but are not ordinary executable or library pages. No per-file hash, UUID, Objective-C method list, or code-signing identity from these private app and mobile paths is published. The protected descendants may contain additional files of any type. Mutable files can appear or disappear even when a mount table remains unchanged.

## Read-only device hash follow-up

With the same pinned root SSH route, a later read-only `sha256sum -z` pass hashed all **303 Data** and **3 Mobile data** candidate paths. It returned 306 unique SHA-256 records, no missing candidate and no stderr, and exited zero. This proves each candidate path had readable contents at the hash observation time; it does **not** prove that its contents or size were unchanged since the earlier type pass. The private result JSON has SHA-256 `961399dcd5fa4a4f2cb07a7c47c75c1ad2a42511202bdd2f35666cc30a4e1f52` and is tied to the private snapshot manifest SHA-256 above. The paths and individual hashes remain under ignored `.local`.

At this hash stage, no candidate bytes had been acquired locally, so Mach-O headers and UUIDs were not yet checked. The 73 protected directories and Mobile data's 34-path churn still limit coverage.

## Private byte and header verification

A subsequent **read-only tar transfer** acquired all 306 candidate files into ignored `.local`. Every local SHA-256 matched its earlier device-side hash, and all acquired sizes still matched the private snapshot sizes. The transfer exited zero; no candidate was missing, changed, or truncated. Its local archive reader accepted only requested regular-file members and stored files under opaque private names rather than mirroring app paths. The private acquisition manifest has SHA-256 `28493cdab9ea4b22c3200dc3f560b947f867e94db6739dcef82a07b6ecd7de3d`, referencing the private hash manifest above. Raw transfer diagnostics remain private.

All 306 acquired files had parseable Mach-O headers and UUIDs, yielding **312 architecture slices**: 192 arm64e and 120 arm64. Data accounts for 303 files and 307 slices; Mobile data accounts for 3 files and 5 slices. Five Data files are dSYM companions rather than ordinary launchable code. This verifies **the reachable candidates from those type passes**, not every possible code-bearing file in either partial mount: 73 protected directories remain unreadable, Mobile data changed between metadata passes, and scripts or embedded formats were outside the type filter. No private path, individual file hash, UUID, or binary is published.

## Private static metadata pass

The 306 byte-verified files were hard-linked into an ignored, permission-restricted `.local` analysis tree and rechecked against device-side SHA-256 values. Existing Mach-O analyzers then checked all **312 slices** for direct library loads, named `__text` symbols, Swift dump metadata, and embedded signing structures. The private aggregate validator checked each result against the exact file hash, architecture, and UUID in the acquisition manifest. Only the counts below are published; individual app paths, method names, symbols, dependency names, entitlements, and signing identities remain private.

- **Data:** 303 files and 307 slices. Objective-C: 281 parsed with 226,114 methods, 14 no info, three failed, and five dSYM not applicable. Other static results: 10,243 direct loads, 146,366 named `__text` symbols, 107,258 Swift declarations, and 302 CodeDirectories.
- **Mobile data:** Three files and five slices. Objective-C: two parsed with 13 methods and one no-info result. Other static results: 18 direct loads, eight named `__text` symbols, no Swift declarations, and five CodeDirectories.

The three Objective-C failures all have `LC_ENCRYPTION_INFO_64` with `crypt_id=1`, and each encrypted file range overlaps at least one `__objc_*` section. Two class dumps returned read errors; the third exited zero but emitted malformed, nonprintable interface data. This is an on-disk encryption limit, not evidence of zero methods. Their method counts remain **unknown**. The private failure evidence JSON has SHA-256 `043d15fa38f23ce185ea7781de1e769fe210dbd2d9ed13171b0353bdb3a4e1bf`; no decrypted memory or runtime behavior was inspected. The five dSYM companions are debug-symbol files and were not treated as Objective-C code images. Across both mounts, 105 files yielded no named `__text` symbols; 83 slices reported no Swift information, 39 Swift dumps were partially parsed, and two slices had Swift sections the dumper could not parse. Five slices had no embedded signature; 307 had a parseable CodeDirectory. These are static metadata results, not proof of runtime loading, signature trust, or a complete callable surface.

The private aggregate is saved at `.local/live-device-data-followup-20261106/analysis-full/aggregate-summary.json`. Its validator is [`tools/summarize_private_data_macho_analysis.py`](../../tools/summarize_private_data_macho_analysis.py); the input hard-link preparation is [`tools/prepare_private_data_macho_analysis.py`](../../tools/prepare_private_data_macho_analysis.py). Neither the private aggregate nor per-file analysis outputs are site data. Protected directories, Mobile data churn, scripts, and embedded formats remain outside this pass.

## Reproduce and next work

With the saved, pinned root SSH route to this exact phone, make a private metadata snapshot of each mount and run `find <MOUNT> -xdev -type f -exec file -0 -0 -- {} +` without crossing mount boundaries. Preserve NUL-delimited results and stderr privately. Compare each emitted path set with its snapshot, count descriptions containing `Mach-O` or `universal binary`, and treat every inaccessible directory and changed path as an explicit limit. The [collection procedure](../../docs/live-device-collection.md) explains the private snapshot format; the [public mount catalog](../../catalog/ios/23A355/live-coverage.json) retains the earlier observation's counts.

The [private hash and acquisition procedures](../../docs/live-device-collection.md) validate the saved snapshot, NUL-delimited type results, exact device build, tar members, and local byte identity without printing private paths. The private metadata pass adds broad static interface and dependency counts; deeper per-library work should select reviewed system components rather than expose app-specific details. A cause for the 73 access denials requires separate evidence. Script and embedded-code formats remain outside this Mach-O type pass.
